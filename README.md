# Tic-Tac-Toe API

HTTP API для игры в крестики-нолики: против компьютера или против другого пользователя. Есть регистрация и вход по JWT (пара access + refresh токенов), список доступных игр, присоединение к игре, получение игры, история завершённых игр, таблица лидеров по доле побед и информация о пользователе. Написан на Go, данные хранятся в PostgreSQL. Учебный проект школы 21 (Go_Bootcamp).

Клиент присылает только то, что вправе решать сам: игровое поле со своим ходом или режим новой игры. Всё остальное (чей сейчас ход, победитель, состояние игры, ответный ход компьютера) вычисляет и хранит сервер. Компьютер играет алгоритмом «Минимакс» оптимально: выиграть у него нельзя, лучший результат игрока это ничья.

## Возможности

- Игра против компьютера (алгоритм «Минимакс») и игра двух пользователей.
- Состояния игры: ожидание игроков, ход игрока, ничья, победа игрока. Окончание игры определяется состоянием, которое сервер пересчитывает после каждого хода.
- Значки игроков хранятся в игре: создатель играет крестиками и ходит первым, присоединившийся играет ноликами.
- Создание игры с пользователем или с компьютером, список доступных игр, присоединение к игре.
- Проверка хода на стороне сервера: ходит участник, и именно в свою очередь, прежние ходы не изменены, добавлен ровно один ход своим значком, игра не закончена.
- Получение игры по UUID (только участникам), информации о пользователе по UUID и о себе по access-токену.
- История завершённых игр пользователя (победа или ничья), новые сверху.
- Таблица лидеров: первые N игроков по доле побед. Игры с компьютером учитываются, игроки без завершённых игр в таблицу не попадают.
- Хранение в PostgreSQL: состояние переживает перезапуск сервера.
- Регистрация и вход по логину и паролю, пароли хранятся только в виде хеша bcrypt. Вход выдаёт пару JWT: короткий access-токен для запросов и долгоживущий refresh-токен для обновления пары.
- Защита маршрутов middleware `UserAuthenticator`: регистрация, вход и обновление токенов открыты, остальные маршруты требуют заголовка `Authorization: Bearer {accessToken}`.
- Корректное завершение работы: остановка сервера и закрытие пула соединений через жизненный цикл `uber/fx`.
- Запуск одной командой через Docker Compose: база данных, миграции и сервер.

## Правила игры

**Поле** это матрица 3×3: `0` пустая клетка, `1` крестик, `-1` нолик.

**Игроки и значки.** Создатель игры играет крестиками и ходит первым. Второй игрок (человек или компьютер) играет ноликами. В игре с компьютером место нолика принадлежит компьютеру, поэтому в ответе нет поля `nought_player_id`.

**Ход.** Игрок присылает полное поле с одной новой клеткой своего значка. Ход допустим, если одновременно выполнено:

1. игра идёт (есть второй игрок, она не закончена);
2. сейчас очередь этого игрока;
3. все прежние клетки остались как были;
4. добавлена ровно одна клетка, и это значок игрока (чей значок ходит, сервер определяет по числу крестиков и ноликов на поле).

**Конец игры.** Победа это три одинаковых значка подряд по строке, столбцу или диагонали. Ничья это заполненное поле без победителя. Состояние пересчитывается после каждого хода, в том числе после ответного хода компьютера.

**Против компьютера** ответный ход делается в том же запросе, что и ход игрока, отдельный запрос не нужен. Если игрок своим ходом закончил игру, компьютер не ходит.

### Состояния игры

```mermaid
stateDiagram-v2
    [*] --> waiting_players: создана игра с человеком
    [*] --> player_turn: создана игра с компьютером
    waiting_players --> player_turn: второй игрок присоединился
    player_turn --> player_turn: ход принят
    player_turn --> won: три в ряд
    player_turn --> draw: поле заполнено
```

| Состояние (`state`) | Значение | Описание |
|---|---|---|
| `waiting_players` | 0 | игра с человеком создана, ждёт второго игрока; ходить нельзя |
| `player_turn` | 1 | игра идёт, `turn_player_id` показывает, чей ход |
| `draw` | 2 | ничья, `turn_player_id` и `winner_id` нет |
| `won` | 3 | победа, `winner_id` это победитель; если победил компьютер, `winner_id` нет |
| `archived` | 4 | служебное: старые игры, созданные до появления игроков; ходить в них нельзя |

Если у игры нет игрока, в базе хранится `NULL`, в домене `uuid.Nil`, а в JSON поле пропускается.

## Архитектура

Проект построен по слоистой архитектуре с правилом зависимостей Clean Architecture: зависимости направлены к центру, а центр ничего не знает о внешнем мире.

```mermaid
flowchart LR
    web --> domain
    application --> domain
    datasource --> domain
    di -.-> web
    di -.-> application
    di -.-> datasource
```

Сплошные стрелки означают «импортирует». Слои `web`, `application` и `datasource` не знают друг о друге и общаются только через интерфейсы из `domain`. Связывает их единственное место, слой `di`.

### Слои

| Слой | Ответственность |
|---|---|
| `domain` | Центр. Модели, ошибки, интерфейсы репозиториев и сервисов, правила игры. Не зависит от БД, HTTP и внешних библиотек, кроме `uuid`. |
| `application` | Сценарии использования: регистрация и проверка логина и пароля, создание игры, присоединение, ход, получение игры. Опирается на интерфейсы из `domain`. |
| `datasource` | Инфраструктура: PostgreSQL. Реализации репозиториев на pgx, мапперы между моделями БД и домена, миграции. |
| `web` | Контракты с API: HTTP-хендлеры, JSON-модели, валидация входных данных, middleware авторизации. |
| `di` | Граф зависимостей на `uber/fx`, регистрация маршрутов, запуск сервера. |

### Разделение логики

Бизнес-логика разделена на два вида:

- **Правила предметной области** (`domain/domainrule`): кто выиграл, заполнено ли поле, чей сейчас значок, пересчёт состояния игры, лучший ход компьютера (Минимакс), допустим ли переход от старого поля к новому, может ли игрок ходить сейчас, может ли пользователь смотреть игру, можно ли присоединиться. Не зависят от БД и HTTP.
- **Сценарии** (`application/appservice`): что приложение делает по запросу. Например, «достать игру, проверить права и ход, пересчитать состояние, сохранить».

### Обработка хода

`POST /game/{id}` проходит такой путь:

1. `UserAuthenticator` читает заголовок `Authorization: Bearer {accessToken}`, проверяет подпись и срок токена через `JwtProvider`, извлекает UUID пользователя и кладёт его в контекст запроса. При неудаче отвечает `401` с заголовком `WWW-Authenticate: Bearer`, хендлер не вызывается.
2. `GameHandler.MakeMove` берёт UUID игры из адреса, UUID пользователя из контекста и поле из тела (`MakeMoveRequest`), переводит поле в доменную доску.
3. `GameService.MakeMove` достаёт игру из `GameRepository` (нет игры: `ErrGameNotFound`), проверяет право хода (`ValidateTurn`) и сам ход на копии-кандидате (`ValidateMove`), пересчитывает состояние (`UpdateState`).
4. Если игра против компьютера и всё ещё идёт, компьютер делает ответный ход (`NextMove`), и состояние пересчитывается ещё раз.
5. `GameRepository.Save` сохраняет игру (upsert), хендлер возвращает игру в формате `GameResponse`.

## Структура проекта

Каждый слой это отдельный Go-модуль со своим `go.mod`, модули объединены через `go.work`. Внутри слоя каждая папка это пакет с одной ответственностью. К имени пакета добавлена короткая приставка слоя (`domain…`, `app…`, `ds…`, `web…`), чтобы по имени было видно слой, а редактор не путал одинаково названные пакеты.

```
.
├── cmd/app/                   точка входа: fx.New(di.Module).Run()
├── internal/
│   ├── domain/
│   │   ├── domainmodel/       Game, GameState, Board, Cell, User, SignUpRequest, LeaderboardEntry
│   │   ├── domainerror/       ошибки предметной области
│   │   ├── domainrepository/  интерфейсы репозиториев
│   │   ├── domainservice/     интерфейсы сервисов (GameService, UserService, AuthService)
│   │   └── domainrule/        правила игры, Минимакс
│   ├── application/
│   │   └── appservice/        реализации сервисов
│   ├── datasource/
│   │   ├── dsmodel/           структуры строк таблиц (теги db)
│   │   ├── dsmapper/          dsmodel <-> domainmodel
│   │   ├── dsrepository/      репозитории на pgx
│   │   ├── dspostgres/        создание пула соединений
│   │   └── migrations/        SQL-миграции
│   ├── web/
│   │   ├── webmodel/          JSON-модели запросов и ответов
│   │   ├── webmapper/         webmodel <-> domainmodel, валидация
│   │   ├── webhandler/        HTTP-хендлеры
│   │   ├── webmiddleware/     UserAuthenticator
│   │   └── webcontext/        UUID пользователя в контексте запроса
│   └── di/                    граф зависимостей, маршруты, запуск сервера
├── docker-compose.yml         описание контейнеров: db, migrate, app
├── Dockerfile                 сборка образа приложения (два этапа)
├── .dockerignore              что не копировать в образ (.git, .env, .DS_Store)
├── .env.example               образец переменных окружения (для запуска без Docker)
└── go.work
```

## Быстрый старт

Весь проект (база данных, миграции и сервер) запускается в Docker одной командой. Устанавливать Go, PostgreSQL и утилиту `migrate` не нужно.

### Требования

- Docker с плагином Compose. На macOS и Windows это Docker Desktop: перед любыми командами `docker` приложение должно быть запущено. На Linux это Docker Engine и пакет `docker-compose-plugin`.
- Свободные порты `8080` (сервер) и `5433` (база данных, нужен для подключения с компьютера).
- `curl`, `jq` и `uuidgen` для ручного тестирования.
- Go 1.27 или новее нужен только для разработки без контейнера (раздел [Разработка](#разработка)).

### Запуск

Из корня проекта (там, где лежит `docker-compose.yml`):

```bash
docker compose up -d --build
```

Флаги: `up` создаёт и запускает контейнеры, `-d` (*detached*) запускает их в фоне и оставляет терминал свободным, `--build` собирает образ приложения заново. Первый запуск дольше остальных: скачиваются образы и библиотеки Go.

Что происходит по порядку:

1. Запускается база данных `db`. Docker каждые 2 секунды спрашивает, готова ли она.
2. Когда база готова, контейнер `migrate` создаёт таблицы и завершается.
3. Когда миграции прошли успешно, собирается и запускается сервер `app`.

### Проверка

```bash
docker compose ps -a
```

Ожидаемые состояния: `db` это `Up (healthy)`, `migrate` это `Exited (0)` (код `0` значит «выполнено успешно»), `app` это `Up`.

Пробный запрос:

```bash
curl -i -X POST http://localhost:8080/signup -d '{"login":"anna","password":"secret123"}'
```

Ожидается `201 Created`. Если ответ `409 Conflict`, такой логин уже есть: возьмите другой. Полный сценарий проверки описан в разделе [Ручное тестирование](#ручное-тестирование-curl).

### Остановка

```bash
docker compose down
```

Контейнеры останавливаются и удаляются, данные базы остаются. Чтобы удалить и данные, см. раздел [Docker](#docker).

## Docker

### Как это устроено

Каждый сервис из `docker-compose.yml` это отдельный контейнер:

| Сервис | Образ | Что делает | Как работает |
|---|---|---|---|
| `db` | `postgres:16` (готовый, с Docker Hub) | база данных PostgreSQL | постоянно |
| `migrate` | `migrate/migrate` (готовый, с Docker Hub) | применяет SQL-миграции из `internal/datasource/migrations` | выполняет работу и завершается |
| `app` | собирается из `Dockerfile` | сервер API | постоянно |

Порядок запуска задан зависимостями:

```mermaid
flowchart LR
    db -- "здорова (healthcheck)" --> migrate
    migrate -- "завершён с кодом 0" --> app
```

Если миграция завершится ошибкой, сервер `app` не запустится, и проблема будет видна сразу.

### Файлы

| Файл | Назначение |
|---|---|
| `docker-compose.yml` | описывает три сервиса, их порты, переменные, диск базы и порядок запуска |
| `Dockerfile` | рецепт сборки образа приложения |
| `.dockerignore` | список того, что не копируется в образ: `.git`, `.env`, `.DS_Store`. Так пароли из `.env` и история репозитория не попадают в образ |

`Dockerfile` состоит из двух этапов (*multi-stage build*):

1. **Сборка.** Берётся образ `golang:1.27`, копируется проект, программа компилируется командой `go build` с `CGO_ENABLED=0`, то есть в один самодостаточный файл. Кэш библиотек Go (`--mount=type=cache`) ускоряет повторные сборки.
2. **Итоговый образ.** Берётся маленький `alpine:3.20`, в него копируется только готовый файл `/app`. Компилятор Go в итоговый образ не попадает, поэтому он небольшой. `EXPOSE 8080` лишь документирует порт сервера, а реальный проброс порта задан в `docker-compose.yml`.

### Сеть и адреса

Внутри контейнера `localhost` означает сам этот контейнер, а не ваш компьютер. Контейнеры Compose находят друг друга по имени сервиса:

| Откуда обращаются | Адрес базы |
|---|---|
| контейнеры `app` и `migrate` | `db:5432` (имя сервиса и внутренний порт) |
| ваш компьютер (`psql`, `go run .`) | `localhost:5433` (проброшенный порт) |

Запись `ports: "5433:5432"` читается так: порт `5433` компьютера ведёт на порт `5432` внутри контейнера. Для сервера записано `8080:8080`, поэтому все запросы идут на `http://localhost:8080`.

Строка подключения собирается из значений сервиса `db`: `postgres://<POSTGRES_USER>:<POSTGRES_PASSWORD>@db:5432/<POSTGRES_DB>`. Если вы меняете пользователя, пароль или имя базы, поменяйте их во всех местах `docker-compose.yml` (в `db`, `migrate` и `app`).

### Данные

Данные PostgreSQL лежат на томе (*volume*) `pgdata`, подключённом к папке `/var/lib/postgresql/data` контейнера. Том живёт отдельно от контейнера, поэтому данные сохраняются при `docker compose down`, перезапуске и пересборке. К имени тома Docker добавляет название папки проекта. Удаляются данные только командой `docker compose down -v`.

При самом первом запуске база пустая, таблицы создают миграции.

### Команды

Все команды выполняются из корня проекта.

| Команда | Для чего |
|---|---|
| `docker compose up -d --build` | собрать образ и запустить всё в фоне |
| `docker compose up -d` | запустить без пересборки образа |
| `docker compose ps -a` | показать состояние контейнеров, включая завершённые (`-a` значит *all*) |
| `docker compose logs app` | логи сервера (также `logs db`, `logs migrate`) |
| `docker compose logs -f app` | следить за логами в реальном времени, выход `Ctrl+C` (`-f` значит *follow*) |
| `docker compose stop` | остановить контейнеры, не удаляя их |
| `docker compose start` | запустить остановленные контейнеры |
| `docker compose down` | остановить и удалить контейнеры и сеть, данные базы остаются |
| `docker compose down -v` | то же и удалить том `pgdata`, то есть **все данные базы** (`-v` значит *volumes*) |
| `docker compose up migrate` | применить миграции (база запустится, если ещё не работает) |
| `docker compose exec db psql -U tictactoe -d tictactoe` | открыть консоль PostgreSQL внутри контейнера; выход `\q` |
| `docker compose exec db psql -U tictactoe -d tictactoe -c "\dt"` | выполнить один запрос и выйти (здесь `\dt` показывает список таблиц) |
| `docker compose config` | проверить `docker-compose.yml` и показать итоговую конфигурацию |

В командах с `compose` указывается имя **сервиса** из файла (`db`, `migrate`, `app`), а не имя контейнера (`tictactoe-db-1`): имя сервиса задано файлом и не меняется, а имя контейнера Compose составляет сам.

После изменения кода образ нужно пересобрать: `docker compose up -d --build`. Без `--build` будет работать старая версия.

### Миграции в Docker

- Миграции применяются автоматически при каждом `docker compose up`. Уже применённые повторно не выполняются, утилита помнит их в таблице `schema_migrations`.
- Папка `internal/datasource/migrations` подключена к контейнеру `migrate`. Новую миграцию (пара файлов `.up.sql` и `.down.sql` со следующим номером) достаточно положить в папку и выполнить `docker compose up migrate`.
- Откат последней миграции:

```bash
docker compose run --rm migrate -path=/migrations \
  -database="postgres://tictactoe:tictactoe@db:5432/tictactoe?sslmode=disable" down 1
```

Здесь `run --rm` запускает одноразовый контейнер и удаляет его после работы, а слова после имени сервиса заменяют `command` из `docker-compose.yml`. Параметр `sslmode=disable` допустим только для локальной учебной базы.

### Если что-то пошло не так

| Симптом | Вероятная причина | Что делать |
|---|---|---|
| `Cannot connect to the Docker daemon` | не запущен Docker Desktop | запустите приложение Docker Desktop |
| `port is already allocated` или `address already in use` | порт `5433` или `8080` занят: другой контейнер, локальный PostgreSQL или сервер, запущенный через `go run .` | найдите занявшего через `docker ps`, остановите его |
| `app` сразу завершается | ошибка при запуске | `docker compose logs app` |
| `migrate` завершился с кодом не `0`, `app` не запустился | ошибка в SQL или в строке подключения | `docker compose logs migrate` |
| `database "..." does not exist` в логах `db` | имя базы в строке подключения не совпадает с `POSTGRES_DB` | исправьте имя в `docker-compose.yml` |
| поведение не изменилось после правки кода | образ не пересобран | `docker compose up -d --build` |
| нужна чистая база | | `docker compose down -v`, затем `docker compose up -d --build` |

## Конфигурация

| Переменная | Обязательная | Описание | Пример |
|---|---|---|---|
| `DATABASE_URL` | да | строка подключения к PostgreSQL | `postgres://tictactoe:tictactoe@db:5432/tictactoe` |

Откуда берётся значение:

- **В Docker** переменная задана в `docker-compose.yml` (сервис `app`), файл `.env` не нужен. Адрес указывает на `db:5432`, то есть на контейнер с базой внутри сети Compose.
- **При запуске без контейнера для приложения** (раздел [Разработка](#разработка)) значение берётся из `.env`, и адрес указывает на проброшенный порт: `postgres://tictactoe:tictactoe@localhost:5433/tictactoe`.

Порт сервера (`8080`) задан в коде. Файл `.env` добавлен в `.gitignore` и не должен попадать в репозиторий, а `.dockerignore` не пускает его в образ.

## API

Базовый адрес: `http://localhost:8080`. Тела запросов и ответов в формате JSON, заголовок `Content-Type` для запросов не обязателен.

| Метод и путь | Доступ | Описание |
|---|---|---|
| `POST /signup` | открыт | регистрация пользователя |
| `POST /signin` | открыт | проверка логина и пароля, возвращает пару JWT |
| `POST /update/access` | открыт | новый access-токен (и новая пара) по refresh-токену |
| `POST /update/refresh` | открыт | ротация пары по refresh-токену |
| `POST /game` | Bearer | создание игры (с человеком или с компьютером) |
| `GET /game` | Bearer | список игр, к которым можно присоединиться |
| `GET /game/completed` | Bearer | завершённые игры пользователя (победа или ничья), новые сверху |
| `GET /game/leaderboard` | Bearer | таблица лидеров: первые N игроков по доле побед; N в `?limit=`, по умолчанию 10 |
| `POST /game/{id}/join` | Bearer | присоединение к игре |
| `GET /game/{id}` | Bearer | получение игры (участникам) |
| `POST /game/{id}` | Bearer | ход в игре |
| `GET /user/{id}` | Bearer | информация о пользователе по UUID |
| `GET /user/me` | Bearer | информация о текущем пользователе по токену |

### Авторизация

Используется JWT (RFC 7519): заголовок `Authorization: Bearer {accessToken}`. Сервер не хранит сессий: подлинность доказывает подпись HMAC-SHA256 секретом из окружения (`JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`), срок годности — полем `exp` внутри токена. Access-токен живёт 15 минут и предъявляется в каждом запросе к защищённым маршрутам. Refresh-токен живёт 30 дней и используется только в `POST /update/*`: сервер проверяет его, извлекает UUID и выдаёт свежую пару (ротация). На защищённых маршрутах при отказе сервер отвечает `401` и заголовком `WWW-Authenticate: Bearer`.

### Формат игры (`GameResponse`)

Все методы, которые возвращают игру, отдают один и тот же объект:

```json
{
  "id": "d44a1dd5-eb55-4407-ab83-a842133da6b0",
  "board": [[-1, 1, 0], [0, 1, 0], [0, 0, 0]],
  "state": "player_turn",
  "vs_computer": false,
  "turn_player_id": "c84564f6-6ad2-4b9d-be85-f60283aae49f",
  "cross_player_id": "c84564f6-6ad2-4b9d-be85-f60283aae49f",
  "nought_player_id": "fe048159-9192-412e-b527-b808352d8d47",
  "created_at": "2026-11-09T13:41:32.495322Z"
}
```

| Поле | Описание |
|---|---|
| `id` | UUID игры |
| `board` | поле 3×3: `0` пусто, `1` крестик, `-1` нолик |
| `state` | `waiting_players`, `player_turn`, `draw`, `won`, `archived` |
| `vs_computer` | игра против компьютера |
| `turn_player_id` | чей ход; только в состоянии `player_turn`; в игре с компьютером при ходе компьютера не бывает, потому что он ходит в том же запросе |
| `winner_id` | победитель; только в состоянии `won`, и только если выиграл человек |
| `cross_player_id` | игрок, который ходит крестиками |
| `nought_player_id` | игрок, который ходит ноликами; в игре с компьютером и до присоединения нет |
| `created_at` | дата создания игры в UTC, формат RFC 3339 с микросекундами; у игр, созданных до миграции `000004`, поля нет |

Поля без значения в ответе отсутствуют.

### `POST /signup`

Регистрирует пользователя.

```json
{ "login": "anna", "password": "qwerty" }
```

Правила валидации: логин не пустой (пробелы по краям отбрасываются) и не содержит символ `:`; пароль не пустой и не длиннее 72 байт (ограничение bcrypt).

| Код | Когда |
|---|---|
| `201 Created` | пользователь создан, тело пустое |
| `400 Bad Request` | некорректный JSON, недопустимый логин или пароль |
| `409 Conflict` | логин уже занят |

### `POST /signin`

Проверяет учётные данные. Тело JSON, заголовок `Authorization` не нужен. Ответ `200 OK`:

```json
{ "type": "Bearer", "accessToken": "eyJhbG...", "refreshToken": "eyJhbG..." }
```

| Код | Когда |
|---|---|
| `200 OK` | логин и пароль верные, в ответе пара токенов |
| `400 Bad Request` | некорректный JSON, недопустимый логин или пароль |
| `401 Unauthorized` | логин и пароль неверные |

Ответ на несуществующий логин и на неверный пароль одинаковый, чтобы по нему нельзя было перебором узнать зарегистрированные логины.

### `POST /update/access`, `POST /update/refresh`

Обновление пары по refresh-токену. Тело JSON:

```json
{ "refreshToken": "eyJhbG..." }
```

Оба endpoint'а проверяют подпись и срок refresh-токена, извлекают UUID и возвращают свежую пару в формате ответа `POST /signin` (ротация: прежняя пара заменяется новой целиком). Заголовок `Authorization` не требуется — access-токен к этому моменту обычно уже истёк.

| Код | Когда |
|---|---|
| `200 OK` | refresh-токен верный, в ответе новая пара |
| `400 Bad Request` | некорректный JSON, пустой токен |
| `401 Unauthorized` | подпись не сошлась или срок вышел |

### `GET /user/me`

Возвращает `id` и `login` текущего пользователя. UUID берётся из проверенного access-токена, указывать его в адресе не нужно. Требует заголовка `Authorization: Bearer {accessToken}`; без него или с неверным токеном — `401`.

### `POST /game`

Создаёт игру. Создатель становится игроком с крестиками. Тело необязательное, по умолчанию игра с человеком.

```json
{ "vs_computer": true }
```

Игра с человеком создаётся в состоянии `waiting_players`. Игра с компьютером сразу в состоянии `player_turn`, ход за создателем.

| Код | Когда |
|---|---|
| `201 Created` | игра создана, в теле игра |
| `400 Bad Request` | некорректный JSON |
| `401 Unauthorized` | не авторизован |

### `GET /game`

Возвращает массив игр, к которым пользователь может присоединиться: состояние `waiting_players`, не против компьютера, создатель не сам пользователь. Если таких нет, возвращается пустой массив `[]`.

| Код | Когда |
|---|---|
| `200 OK` | массив игр |
| `401 Unauthorized` | не авторизован |

### `POST /game/{id}/join`

Присоединяет пользователя к игре с человеком: он становится игроком с ноликами, игра переходит в `player_turn`, первым ходит создатель. Тело не нужно.

| Код | Когда |
|---|---|
| `200 OK` | присоединился, в теле игра |
| `400 Bad Request` | некорректный UUID |
| `401 Unauthorized` | не авторизован |
| `403 Forbidden` | своя собственная игра |
| `404 Not Found` | игры нет |
| `409 Conflict` | к игре нельзя присоединиться (уже началась, закончена или против компьютера) |

### `GET /game/completed`

Возвращает массив завершённых игр, в которых участвует текущий пользователь: состояние `won` (победа любого из игроков, включая победу компьютера) или `draw` (ничья). Игры, которые пользователь проиграл, тоже входят в список. Сортировка по `created_at` от новых к старым, игры без даты (`NULL`) в конце. Если завершённых игр нет, возвращается `[]`.

| Код | Когда |
|---|---|
| `200 OK` | массив игр |
| `401 Unauthorized` | не авторизован |

### `GET /game/leaderboard`

Возвращает таблицу лидеров: не больше N игроков, отсортированных по доле побед. N задаётся параметром `?limit=`, по умолчанию 10.

```bash
curl -s "http://localhost:8080/game/leaderboard?limit=3" -H "Authorization: Bearer ${accessToken}"
```

```json
[
  { "user_id": "c10e14a0-2eda-4cab-af9f-e5f77a978704", "login": "anna", "win_rate": 0.5 },
  { "user_id": "b8d421fc-e3e0-4c8a-bb2c-b7d25c842175", "login": "boris", "win_rate": 0.3333333333333333 }
]
```

| Поле | Описание |
|---|---|
| `user_id` | UUID игрока |
| `login` | логин игрока |
| `win_rate` | доля выигранных игр от всех завершённых, от `0` до `1` |

Как считается:

- Учитываются только завершённые игры: победа (`won`) и ничья (`draw`).
- Каждая игра даёт результат каждому участнику: победа, поражение или ничья. Отдельных колонок «победы» и «поражения» в таблице `games` нет, результат выводится из `state` и `winner_id`.
- `win_rate = победы / (победы + поражения + ничьи)`.
- Игры против компьютера считаются наравне с играми людей: победа над компьютером — победа, поражение компьютеру — поражение (в базе у такой игры `winner_id` пустой). Минимакс не проигрывает, поэтому накрутить рейтинг на компьютере нельзя.
- Игроки без завершённых игр в таблицу не попадают: их доля не определена (0 из 0).
- Порядок: `win_rate` по убыванию, при равенстве выше тот, у кого больше завершённых игр, при равенстве — по алфавиту логина.
- Таблица не хранится: она считается запросом из `games` и `users` при каждом обращении и не может разойтись с играми.

| Код | Когда |
|---|---|
| `200 OK` | массив игроков; `[]`, если завершённых игр ещё нет |
| `400 Bad Request` | `limit` не число или меньше 1 |
| `401 Unauthorized` | не авторизован |

### `GET /game/{id}`

Возвращает игру. Смотреть может только участник (создатель или присоединившийся). Архивные игры (`archived`) без участников видны любому авторизованному пользователю.

| Код | Когда |
|---|---|
| `200 OK` | в теле игра |
| `400 Bad Request` | некорректный UUID |
| `401 Unauthorized` | не авторизован |
| `403 Forbidden` | пользователь не участник игры |
| `404 Not Found` | игры нет |

### `POST /game/{id}`

Делает ход игрока и возвращает обновлённую игру. В игре с компьютером в ответе уже есть ответный ход компьютера. В теле только поле, UUID игры берётся из адреса, игрок из авторизации.

```json
{ "board": [[1, 0, 0], [0, 0, 0], [0, 0, 0]] }
```

| Код | Когда |
|---|---|
| `200 OK` | ход принят, в теле игра |
| `400 Bad Request` | некорректный UUID или JSON; поле не 3×3; недопустимое значение клетки; изменены прежние ходы; новый ход не один; ход не своим значком |
| `401 Unauthorized` | не авторизован |
| `403 Forbidden` | пользователь не участник игры |
| `404 Not Found` | игры нет (новая игра при ходе больше не создаётся) |
| `409 Conflict` | сейчас не очередь игрока; игра ещё не началась (нет второго игрока); игра закончена |
| `500 Internal Server Error` | внутренняя ошибка (детали пишутся в лог, клиенту отдаётся `internal error`) |

Различие между `400` и `409`: `400` это запрос неверный по содержанию независимо от состояния игры (кривой JSON, не 3×3, чужие клетки стёрты). `409` это запрос сам по себе корректный, но не подходит текущему состоянию игры (не ваш ход, игра закончена).

### `GET /user/{id}`

Возвращает пользователя по UUID. Хеш пароля клиенту не отдаётся. Доступен любому авторизованному пользователю: по `cross_player_id` и `nought_player_id` из игры можно узнать логины игроков.

```json
{ "id": "bb02f4b3-5fc3-49bf-8c25-b1fe0b3840cd", "login": "anna" }
```

| Код | Когда |
|---|---|
| `200 OK` | пользователь найден |
| `400 Bad Request` | некорректный UUID |
| `401 Unauthorized` | не авторизован |
| `404 Not Found` | пользователя нет |

## Модель данных

Схема создаётся миграциями из `internal/datasource/migrations`.

**`users`** (миграция `000002`)

| Колонка | Тип | Ограничения |
|---|---|---|
| `id` | `UUID` | `PRIMARY KEY` |
| `login` | `TEXT` | `NOT NULL`, `UNIQUE` |
| `password_hash` | `TEXT` | `NOT NULL`, хеш bcrypt |

**`games`** (миграции `000001`, `000003` и `000004`)

| Колонка | Тип | Ограничения |
|---|---|---|
| `id` | `UUID` | `PRIMARY KEY` |
| `board` | `JSONB` | `NOT NULL`, матрица 3×3 |
| `state` | `INT` | `NOT NULL`, по умолчанию `0`; числа соответствуют таблице состояний (`4` это архив) |
| `turn_player_id` | `UUID` | `NULL`, чей ход |
| `winner_id` | `UUID` | `NULL`, победитель |
| `vs_computer` | `BOOLEAN` | `NOT NULL`, по умолчанию `false` |
| `cross_player_id` | `UUID` | `NULL`, игрок с крестиками |
| `nought_player_id` | `UUID` | `NULL`, игрок с ноликами |
| `created_at` | `TIMESTAMPTZ` | `NULL`, дата создания; заполняется при создании игры в сервисе (UTC), у игр до миграции `000004` пусто |

Миграция `000003` пометила игры, созданные до появления игроков, как `state = 4` (архив) и `vs_computer = true`.

Уникальность логина обеспечивает база данных. Нарушение ограничения (код PostgreSQL `23505`) репозиторий превращает в доменную ошибку `ErrUserExists`. Так проверка остаётся корректной и при одновременной регистрации одного логина.

## Обработка ошибок

Репозитории и сервисы возвращают ошибки предметной области из `domainerror`. Слой `web` ловит ожидаемые через `errors.Is` и переводит в HTTP-статусы. Всё остальное это `500`: внутренние детали (SQL, обёртки `%w`) клиенту не передаются, они попадают только в лог.

| Ошибка домена | HTTP-статус | Где |
|---|---|---|
| `ErrInvalidBoardSize`, `ErrInvalidCellValue` | `400` | ход |
| `ErrBoardModified`, `ErrInvalidMovesCount` | `400` | ход |
| `ErrNotYourTurn`, `ErrGameNotStarted`, `ErrGameOver` | `409` | ход |
| `ErrNotParticipant` | `403` | ход, получение игры |
| `ErrGameNotFound` | `404` | ход, присоединение, получение игры |
| `ErrGameNotJoinable` | `409` | присоединение |
| `ErrJoinOwnGame` | `403` | присоединение |
| `ErrUserNotFound` | `404` | получение пользователя |
| `ErrUserExists` | `409` | регистрация |
| `ErrInvalidCredentials` | `401` | вход, middleware |
| `ErrInvalidLimit` | `400` | таблица лидеров |
| остальные (`ErrBoardFull`, ошибки базы, bcrypt) | `500`, текст `internal error` | везде |

## Ручное тестирование (curl)

Автоматических тестов в проекте нет, поведение проверяется вручную. Ниже сценарий, который проходит все правила игры. Предполагается, что проект запущен (`docker compose up -d --build`, см. [Быстрый старт](#быстрый-старт); подойдёт и `go run .` из `cmd/app`), а команды выполняются в **другом терминале**, подряд, в одной сессии (переменные живут только в ней). Нужны `curl`, `jq` и `uuidgen`.

Ожидаемые коды указаны после каждого блока. Команды `echo` просто печатают заголовки, чтобы вывод читался.

### 0. Подготовка

Адрес, пароль, три новых пользователя и два небольших помощника, чтобы не повторять длинные команды. `post` и `get` печатают тело ответа и после него строку `-> код`.

```bash
BASE=http://localhost:8080
PASS=secret123
A="anna_${RANDOM}"; B="boris_${RANDOM}"; C="clara_${RANDOM}"
signup() { curl -s -X POST "${BASE}/signup" -d "{\"login\":\"${1}\",\"password\":\"${PASS}\"}"; }
signin() { curl -s -X POST "${BASE}/signin" -d "{\"login\":\"${1}\",\"password\":\"${PASS}\"}" | jq -r .accessToken; }
post() { curl -s -H "Authorization: Bearer ${1}" -X POST "${BASE}${2}" -d "${3}" -w "\n-> %{http_code}\n"; }
get() { curl -s -H "Authorization: Bearer ${1}" "${BASE}${2}" -w "\n-> %{http_code}\n"; }
```

Пользователи: `A` создаёт игры, `B` присоединяется и играет, `C` посторонний. Вход выполняется один раз, дальше запросы идут с access-токеном в заголовке.

### 1. Регистрация и вход

```bash
echo "=== регистрация A, B, C ==="
for U in "$A" "$B" "$C"; do signup "$U"; echo "-> $?"; done
echo "=== повторная регистрация A ==="
curl -s -w "\n-> %{http_code}\n" -X POST "${BASE}/signup" -d "{\"login\":\"${A}\",\"password\":\"${PASS}\"}"
echo "=== регистрация с кривым JSON ==="
curl -s -w "\n-> %{http_code}\n" -X POST "${BASE}/signup" -d '{"login":'
echo "=== вход A, B, C ==="
TOKEN_A=$(signin "$A"); TOKEN_B=$(signin "$B"); TOKEN_C=$(signin "$C")
echo "tokens issued"
echo "=== вход с неверным паролем ==="
curl -s -w "\n-> %{http_code}\n" -X POST "${BASE}/signin" -d "{\"login\":\"${A}\",\"password\":\"wrong\"}"
echo "=== защищённый маршрут без токена ==="
curl -s "${BASE}/game" -w "\n-> %{http_code}\n"
echo "=== защищённый маршрут с мусором вместо токена ==="
curl -s -H "Authorization: Bearer garbage.token.here" "${BASE}/game" -w "\n-> %{http_code}\n"
```

| Шаг | Ожидается |
|---|---|
| регистрация A, B, C | три раза `201` |
| повторная регистрация | `409`, `login already exists` |
| кривой JSON | `400`, `invalid request body` |
| вход A, B, C | три непустых access-токена |
| неверный пароль | `401` |
| без токена | `401`, `unauthorized` |
| мусор вместо токена | `401`, `unauthorized` |

### 6. Партия с компьютером

Играем в игру `GAME_CPU`. Компьютер отвечает в том же запросе.

```bash
echo "=== A: крестик в центр ==="
post "$TOKEN_A" "/game/${GAME_CPU}" '{"board":[[0,0,0],[0,1,0],[0,0,0]]}'
```

Ожидается `200`: в поле ваш крестик и один ноль компьютера, состояние `player_turn`, ход снова у `ID_A`. Запишите поле из ответа, оно понадобится ниже. Для типичной партии компьютер отвечает углом `[0][0]`, а дальше блокирует ваши угрозы. Дойдём до ничьей:

```bash

post "$TOKEN_A" "/game/${GAME_CPU}" '{"board":[[-1,1,0],[0,1,0],[0,0,0]]}'
echo "=== A: [1][0] ==="
post "$TOKEN_A" "/game/${GAME_CPU}" '{"board":[[-1,1,0],[1,1,0],[0,-1,0]]}'
echo "=== A: [2][0] ==="
post "$TOKEN_A" "/game/${GAME_CPU}" '{"board":[[-1,1,0],[1,1,-1],[1,-1,0]]}'
echo "=== A: [2][2] ==="
post "$TOKEN_A" "/game/${GAME_CPU}" '{"board":[[-1,1,-1],[1,1,-1],[1,-1,1]]}'
```

Ожидаются ответные ходы компьютера `[2][1]`, `[1][2]`, `[0][2]`, и после последнего хода `200` с `"state":"draw"` (поле заполнено, ни `turn_player_id`, ни `winner_id` нет, компьютер не ходит). Эти поля в командах выше рассчитаны на конкретные ответы компьютера (он детерминирован). Если ответ отличается, берите актуальное поле из последнего ответа и добавляйте в него свою клетку.

## Разработка

Каждый слой это отдельный модуль, поэтому проверки запускаются из папки модуля:

```bash
go build ./...
go vet ./...
```

Для приложения целиком сборка запускается из `cmd/app`. Граф зависимостей `fx` проверяется только при запуске, поэтому после изменений в `di` запустите приложение (`go run .` или `docker compose up -d --build`).

### Запуск сервера без контейнера для приложения

Удобно во время разработки: база и миграции работают в Docker, а сервер запускается на компьютере и не требует пересборки образа. Нужен Go 1.27 или новее.

1. Если контейнер `app` запущен, остановите его, иначе порт `8080` будет занят: `docker compose stop app`.
2. Запустите базу и примените миграции: `docker compose up migrate`.
3. Создайте `.env` из образца: `cp .env.example .env`. В нём должно быть `DATABASE_URL=postgres://tictactoe:***@localhost:5433/tictactoe` и сгенерированные секреты `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET` (генерация: `openssl rand -base64 32`).
4. Загрузите переменные в текущий терминал (нужно в каждом новом терминале): `set -a; source .env; set +a`.
5. Запустите сервер:

```bash
cd cmd/app
go run .
```

Остановка: `Ctrl+C`, сервер завершится корректно. Если `DATABASE_URL` не задан, приложение завершится с понятной ошибкой.

Соглашения:

- Коммиты по [Conventional Commits](https://www.conventionalcommits.org/): `feat`, `fix`, `refactor`, `docs`, `chore`, `test`, с областью в скобках, например `feat(datasource): add user repository`.
- Один коммит на один законченный шаг; сломанный код не коммитится.
- Изменения в `docker-compose.yml` и `Dockerfile` проверяются командой `docker compose up -d --build` и пробным запросом (раздел «Быстрый старт»).
- Правило зависимостей: `domain` ничего не импортирует из проекта; `web`, `application`, `datasource` друг друга не импортируют.
- Новые зависимости добавляются через `go get` в нужном модуле.
- Автоматических тестов в проекте нет, поведение проверяется ручными запросами `curl` (см. раздел выше).

## Принятые решения

- **Сервер решает, клиент просит.** Клиент присылает поле или режим игры. Состояние, чей ход, победитель, значки и UUID игры выдаёт и считает сервер.
- **Игрок отсутствует = пустое значение.** В домене это `uuid.Nil`, в базе `NULL` (`*uuid.UUID` в `dsmodel`), в JSON поле пропускается. Место нолика в игре с компьютером принадлежит компьютеру, это определяется флагом `vs_computer`.
- **Состояние архива.** Игры, созданные до появления игроков, получили состояние `archived` и остаются видимыми, но ходить в них нельзя.
- **Ход проверяется на копии.** Сервис не меняет полученную из репозитория игру, пока ход не проверен.
- **Ответный ход компьютера в том же запросе.** Игра сохраняется один раз, после хода игрока и ответа компьютера, поэтому в базе не бывает игры с «пропущенным» ходом компьютера.
- **`400` и `409`.** `400` для запросов, неверных по содержанию, `409` для корректных запросов, которые не подходят текущему состоянию игры.
- **`403` для постороннего.** Игра с несуществующим id даёт `404`, а чужая игра `403`. UUID нельзя угадать, поэтому раскрытие существования игры допустимо. В системах с чувствительными данными в таком случае часто отвечают `404`.
- **Информация о пользователе открыта любому авторизованному.** Отдаются только `id` и `login`, это нужно, чтобы по UUID из игры узнать логин соперника.
- **Ожидаемые ошибки через `errors.Is`.** Всё остальное это `500` с логом, детали клиенту не показываются.
- **Один контейнер на одну работу.** База, миграции и сервер это отдельные контейнеры. Миграции выполняются одноразовым контейнером перед сервером, поэтому утилиту `migrate` не нужно ставить на компьютер, а сервер не стартует на пустой базе.
- **Двухэтапная сборка образа.** Компилятор Go нужен только для сборки, поэтому в итоговый образ попадает один скомпилированный файл.
- **Таблица лидеров считается запросом.** Отдельной таблицы нет: статистика собирается из `games` и `users` при каждом обращении, поэтому рейтинг не может разойтись с играми и не требует пересчёта при каждой партии.
- **Доля побед, а не отношение побед к поражениям.** `победы / все завершённые игры` всегда лежит от 0 до 1, деления на ноль не бывает, а порядок игроков совпадает с буквальным отношением побед к поражениям и ничьим: это одна и та же величина, сжатая в диапазон.
- **Игры с компьютером идут в рейтинг.** Минимакс в крестиках-ноликах не проигрывает, поэтому набить долю побед на компьютере нельзя, и отделять такие партии от партий людей незачем.
- **Игрок без завершённых игр не показывается.** Доля побед у него не определена (0 из 0), а список всех зарегистрированных с нулями не отвечает на вопрос «кто лучше играет».
- **N передаётся строкой запроса.** N это размер выборки, а не имя ресурса: `?limit=` естественно допускает значение по умолчанию, легко расширяется другими параметрами и не мешает маршруту `GET /game/{id}`.
- **Сортировка из трёх ключей.** Доля, число завершённых игр, логин. С одним ключом при равных долях порядок не определён, и ответ меняется от запроса к запросу.

## Известные ограничения

- Пароль передаётся по сети только один раз — при входе; дальше клиент предъявляет access-токен, сервер проверяет подпись без обращения к базе. Подпись считается HMAC-SHA256, секреты лежат в переменных окружения и не попадают в образ (см. `.dockerignore`). Для реальной системы нужен HTTPS, сейчас сервер работает по HTTP и рассчитан на локальный запуск.
- Использованный refresh-токен сервером не гасится (stateless-проверка: подпись + срок), поэтому технически его можно предъявить повторно до истечения срока. Клиент обязан выбрасывать старую пару целиком. Полное закрытие — deny-list использованных `jti` (следующий шаг hardening'а).
- Два одновременных запроса к одной игре могут перезаписать друг друга (нет блокировок и версионирования). В коммерческих проектах это решают условным `UPDATE` или `SELECT ... FOR UPDATE`.
- У списка доступных игр нет сортировки и ограничения по количеству (`LIMIT`).
- Таблица лидеров считается на каждый запрос, без кэша и материализованного представления: при большом числе игр понадобится либо `MATERIALIZED VIEW` с периодическим обновлением, либо индекс по `state`.
- Верхняя граница `limit` не ограничена: `?limit=1000000` вернёт всех игроков с завершёнными играми.
- `win_rate` отдаётся числом с плавающей точкой без округления, поэтому в ответе возможны длинные дроби вида `0.3333333333333333`. Округление до нужного числа знаков это задача клиента или отдельного поля ответа.
- Игры, созданные до миграции `000004`, не имеют даты создания (`created_at` пусто) и попадают в конец списка завершённых игр.
- Откат миграций делается вручную (см. раздел [Docker](#docker)), автоматически выполняется только применение.
- Проверка пароля запускает bcrypt только на входе (`POST /signin`); защищённые маршруты проверяют подпись токена без обращения к базе и без bcrypt.
- Учётные данные базы (`tictactoe` / `tictactoe`) записаны в `docker-compose.yml` открытым текстом. Для локальной учебной среды это допустимо, в реальной системе пароли передают через секреты или переменные окружения вне репозитория.
- Ответ `401` на `POST /signin` для несуществующего логина приходит быстрее, чем для неверного пароля (для несуществующего bcrypt не запускается), поэтому логины можно различить по времени ответа.
- Автоматических тестов нет.

## Планы развития

- Отзыв refresh-токенов (deny-list использованных `jti`).
- HTTPS для реальной среды.
- Кэш или материализованное представление для таблицы лидеров, если игр станет много.
