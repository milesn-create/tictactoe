# Крестики-нолики

Веб-приложение на Go: HTTP API для игры в крестики-нолики против компьютера. Проект Go_Bootcamp (школа 21), Project 03.

Клиент присылает поле со своим ходом, сервер проверяет, что игрок не жульничал, делает ответный ход и возвращает обновлённое поле. Компьютер играет алгоритмом «Минимакс», то есть идеально: выиграть у него нельзя, в лучшем случае получится ничья. Можно вести несколько игр одновременно, каждая живёт под своим UUID.

## Стек

- Go 1.22 или новее (нужна для маршрутов вида `POST /game/{id}` в `net/http`)
- стандартная библиотека `net/http`, без веб-фреймворков
- `github.com/google/uuid` для идентификаторов игр
- `go.uber.org/fx` для внедрения зависимостей
- `sync.Map` вместо базы данных: игры хранятся в памяти и пропадают при перезапуске

## Запуск

```
cd cmd/app
go run .
```

Сервер слушает порт 8080. Игрок всегда ходит крестиками и первым, компьютер ноликами.

Поле это матрица 3 на 3: `0` пустая клетка, `1` крестик, `-1` нолик. UUID игры придумывает клиент. Если сервер видит UUID, которого у него нет, он считает это началом новой игры.

```
ID=$(uuidgen)
curl -X POST http://localhost:8080/game/$ID \
  -H "Content-Type: application/json" \
  -d "{\"id\":\"$ID\",\"board\":[[0,0,0],[0,1,0],[0,0,0]]}"
```

В ответ придёт то же поле с ответным ходом компьютера:

```
{"id":"...","board":[[-1,0,0],[0,1,0],[0,0,0]]}
```

На следующем запросе нужно прислать поле из ответа плюс один новый крестик.

Ошибки возвращаются с кодом 400 и текстом причины в теле: изменён предыдущий ход, добавлено не ровно по одному ходу за раз, поле не 3 на 3, в клетке недопустимое число, UUID в адресе и в теле не совпадают, игра уже закончена. Неверный метод даёт 405.

## Архитектура

Проект разбит на слои, и каждый слой это отдельный Go-модуль со своим `go.mod`. Модули связаны через `go.work`. Структура папок следует Standard Go Project Layout.

```
cmd/app/            точка входа, одна строка: fx.New(di.Module).Run()
internal/domain/    модели и интерфейс сервиса
internal/datasource/ хранилище, репозиторий, реализация сервиса
internal/web/       HTTP-хендлер и модели для JSON
internal/di/        описание графа зависимостей
```

Зависимости направлены внутрь, к `domain`. Он не импортирует ничего из проекта. `web` и `datasource` знают про `domain`, но не знают друг про друга. Встречаются они только в `di`, где всё собирается.

В `domain` лежат типы `Board` (массив `[3][3]Cell`), `Cell`, `Game`, интерфейс `Service` с тремя методами (следующий ход, проверка поля, проверка конца игры) и общие ошибки.

В `datasource` лежит хранилище на `sync.Map`, репозиторий с методами `Save` и `Get` и структура, которая реализует `domain.Service` и принимает репозиторий. Реализация сервиса находится здесь, а не в `domain`, потому что она зависит от репозитория, а `domain` не должен знать про слой хранения.

В `web` лежит хендлер и модель игры для JSON. Хендлеру для сохранения нужен только метод `Save`, поэтому в `web` объявлен свой маленький интерфейс, и репозиторий ему подходит без явной привязки.

У каждого слоя своя модель игры, а между ними мапперы. В `domain` поле это массив `[3][3]Cell`, и неправильный размер там невозможен. В `web` и `datasource` это `[][]int`, потому что JSON и данные из хранилища могут быть любого размера. Размер и допустимые значения клеток проверяет маппер на входе, поэтому в ядро попадает только корректное поле.

Как проходит один запрос:

1. Хендлер берёт UUID из адреса и читает JSON из тела.
2. Маппер превращает модель `web` в модель `domain` и проверяет размер и значения клеток.
3. Сервис сравнивает присланное поле с сохранённым: старые ходы не тронуты, добавлен ровно один крестик, игра ещё не закончена.
4. Если игра не закончилась, минимакс выбирает ход компьютера.
5. Игра сохраняется, ответ уходит клиенту.

## Что использовано

Алгоритм «Минимакс» перебирает все продолжения партии. Победа компьютера оценивается в `+1`, ничья в `0`, победа игрока в `-1`. Поле `Board` это массив, он копируется по значению, поэтому перебор можно вести на копии, откатывая ход после каждой пробы.

Внедрение зависимостей сделано через `uber/fx`. Конструкторы хранилища, репозитория, сервиса и хендлера регистрируются в `fx.Provide`, а запуск сервера описан в `fx.Invoke`. `fx` сам определяет порядок создания, а хранилище существует в единственном экземпляре. Сервер запускается через `fx.Lifecycle`: при старте в отдельной горутине, при остановке через `Shutdown`, поэтому по `Ctrl+C` приложение завершается корректно.

Ошибки заведены переменными (`ErrGameNotFound`, `ErrBoardModified` и другие) и проверяются через `errors.Is`. По ним хендлер выбирает код ответа.

Маршрутизация сделана средствами `http.ServeMux` из Go 1.22: метод и параметр пути задаются прямо в шаблоне, а значение читается через `r.PathValue("id")`.
